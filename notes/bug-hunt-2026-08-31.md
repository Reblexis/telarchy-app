# Deep bug hunt, 2026-08-31

A full-codebase correctness review of telarchy-app at `884bdbb6` (main).
Ten reviewers read one slice each; every finding below was then re-read
against the source by the reviewing session before it was written down.
Numeric claims were re-derived by running the real modules. Findings that
did not survive that check are in "Reported and rejected" at the end, with
the reason.

**The baseline is green.** `npm test` exits 0, `npm run typecheck` exits 0,
`npm run lint` reports 4 warnings and no errors. Nothing here is a broken
build; all of it is latent, and most of it is invisible until it costs
somebody money.

**Two sentences.** The worst finding is an authorization one: workspace
membership is writable by the workspace's own admin and is then treated as
authority over the member's whole account, so anyone with an account can take
over any participant in three calls (P0-0). The rest of the money path shares
one shape - *read state outside a transaction, decide, then write without a
predicate on the state that was read* - which settlement, void and both
liquidity-injection doors all follow, while `applyCreditsIfSufficient`,
`moveCredits` and `executeTradeInTx` are the codebase's own correct worked
examples of the same problem.

## P0
### 0. Anyone with an account can take over any participant, in three calls

`functions/src/routes/groups.ts:198`, `functions/src/middleware/roles.ts:88`,
`functions/src/routes/agents.ts:1868`

`PUT /api/groups/:id` accepts `memberIds` as any array of strings. It checks
that they are strings and nothing else - not that the ids name real
participants, not that they consented, not that they were ever invited.
`requireSelfOrAdmin` then admits any caller holding `manage` whose target is
returned by `listParticipantsForWorkspace(callerWorkspace)`.

```
POST /api/workspaces {name:"x"}          -> creator gets ALL capabilities
GET  /api/groups                          -> read the Public group id
PUT  /api/groups/<id> {"memberIds":["<any participant id>"]}
        |
        v
   the victim is now "a member of your workspace", so:
   POST   /api/agents/<victim>/keys {"scopes":["*"]}   -> their live wildcard key
   POST   /api/agents/transfer                          -> their whole balance
   POST   /api/agents/<victim>/spend                    -> burn their credits
   DELETE /api/agents/<victim>                          -> delete them platform-wide
   PUT    /api/agents/<victim>/wallet + /withdraw       -> drain to your address (USDC builds)
```

The minted key is not `workspaceLocked` by default, so it authenticates in
every workspace the victim belongs to, including their own private floor.
Only `platformAdmin` accounts are immune, because
`listParticipantsForWorkspace` filters them out.

This is the most serious finding in the review: it is unauthenticated-adjacent
(any signup will do), it is three calls, and it reaches money, identity and
deletion at once.

Fix: `requireSelfOrAdmin`'s admin branch should key on ownership
(`agents.ownerAgentId` / `ownerUserId`), which the parent-agent branch above
it already does correctly, not on workspace membership. Separately,
`PUT /api/groups/:id` should only accept ids that already have a
participant row and a relationship to the workspace.

Tests: none. `functions/src/routes/groups.ts` has no test file at all, and
`requireSelfOrAdmin` is stubbed to a pass-through in every suite that mounts
a route using it (`participant-history.test.ts:27`,
`redemption-not-a-trade.test.ts:51`, `participant-bio.test.ts:29`,
`every-open-anchors.test.ts:35`). Deleting the membership check from
`requireSelfOrAdmin` entirely keeps all 188 test files green.

### 0b. Every new browser account is paid the signup grant twice

`functions/src/routes/userauth.ts:54,83`

`ensureParticipant` reads the price and credits it inside its transaction:

```ts
const grant = await earnCredits('signup_user');
...  await applyCredits(tx, { deltaUnits: toUnits(grant), reason: 'signup_grant' });
```

then calls `claimEarn({ key: 'signup_user' })`, which reads the same price
and credits it again (`services/earnRules.ts:255-270`). The comment directly
above the call says the claim is "recorded so the /earn page can show what is
left and so nothing pays twice". `claimEarn` does not record. It pays.

Every browser signup lands at exactly double the published price - 200 where
the earn table says 100 (migration 0087), or double the `FALLBACK` if the
`earn_rules` row is missing. The `/earn` page reports the single figure
against the doubled balance.

This is a standing violation of market-integrity I5 ("the free routes pay a
person, once"), and it is invisible to
`credit-ledger-reconciliation.test.ts` because both grants write honest
ledger rows, so the balance still equals the ledger sum.

Tests: nothing exercises `ensureParticipant` and asserts a resulting
balance; `earn-claims.test.ts` and `earn-table.test.ts` test `claimEarn` and
`earnCredits` only in isolation.



### 1. Settlement is not idempotent, and three schedules can run it at once

`functions/src/services/predictions.ts:90,137`, `functions/src/routes/cron.ts:88`,
`functions/src/server.ts:152,160`

`posRows` is read outside the transaction, and the settling write is
`.where(and(eq(markets.id, ...), eq(markets.workspaceId, ...)))` with no
`eq(markets.resolved, false)`. Nothing zeroes `positions.shares` on
resolve, so a second pass has full data to pay from again.

Three paths reach it, and no two exclude each other:

```
Cloud Scheduler  */10 * * * *  ->  POST /api/cron/resolve   (NO lock)
in-process timer every 10 min  ->  runDailyResolve          (lock 71001)
every container boot           ->  startupCatchUp           (lock 71005)
                                            |
                                   same work, different key
```

`docs/infra/deploy.md:786` states "Both are idempotent" of these endpoints.
They are idempotent sequentially, not concurrently. Every deploy lands a
candidate revision at `--min-instances 1`, so a boot-time `startupCatchUp`
against production is a routine event, not a rare one.

Failure: a holder of 500 shares in a market settling at payFactor 1.0 is
credited 500 twice from a pool that held 500 once. `distributeLPLeftover`
also runs twice. Both payouts write honest ledger rows, so
`credit-ledger-reconciliation.test.ts` still passes against the doubled
balance.

Fix: add `eq(markets.resolved, false)` to the settling update and abort on
zero rows; read `posRows` inside the transaction; put `/api/cron/resolve`
under `LOCK_KEYS.resolve`; make `startupCatchUp` take the `resolve` lock
for the resolve half.

Tests: none run two resolvers concurrently. `Promise.all([` appears in
exactly one test file in the suite (`earn-claims.test.ts`).

### 2. `voidMarket` has the same shape, and additionally destroys LP credits

`functions/src/services/markets.ts:121,127,143,169-172`

Two defects in one function.

**Concurrency**: `market.resolved` is checked on a row read outside the
transaction, `stakeRows` is aggregated outside it, and the void write again
carries no `resolved = false` predicate. Two concurrent voids refund every
holder twice. `void-refund.test.ts:222` is named *"voiding twice does not
pay twice"* and awaits the first void before starting the second, which is
the case line 121 already handles.

**Arithmetic**: a limit order's budget is debited from the participant's
balance at placement (`routes/predictions.ts:442`, reason
`limit_order_hold`) and never enters `markets.pool`. The void folds the
release back into the same running total it then subtracts from the pool:

```
refunded += await releaseLimitOrdersForMarket(tx, market.id, 'voided');
const lpLeftover = Math.round((pool - refunded) * 100) / 100;
```

Pool 200, one resting order of 150, nobody traded: the LP gets 50 of their
200 back and 150 credits cease to exist. The resolve path at
`predictions.ts:123-126` gets this right and is the direct contrast - it
calls the same release and deliberately keeps it out of `poolLeftover`.

### 3. Every revision runs settlement against the production database

`functions/src/server.ts:152-183`, `functions/src/db/client.ts:107`

The per-request store swap is deliberate and correct: the revision serving
`/beta` today is the one serving telarchy.com tomorrow, so the store is
chosen per request and never per revision. Background work is outside that
by construction and gets `prodDb`.

But `server.ts` arms every timer at boot unconditionally, with no
`K_REVISION` or tag check. So a branch-preview revision - booted by CI's
own smoke test - and the candidate revision (`--min-instances 1`, always
running) each run `runDailyResolve()`, `runDailyRefresh()`, a 10-minute
resolve, a 12-second limit-order sweep and daily maintenance **against live
production data, with unreviewed branch code**, before anyone has looked at
the preview.

`client.ts:39-42` shows the thinking was done for pool size ("safe as a
revision property only because a preview revision can never be published")
and not for job arming.

### 4. Liquidity injection breaks an anchored book's solvency

`functions/src/services/marketLiquidity.ts:22`, and the inlined copy at
`functions/src/routes/predictions.ts:1143`

An anchored market opens with `b = subsidy / max(-ln p, -ln(1-p))`
(`amm.ts:149`), deliberately thinner than `pool/ln2` so the cash subsidy
covers the worst case exactly. Any injection then recomputes
`newLiquidity = newPool / Math.LN2` and rescales the anchor shares by
`newLiquidity / liquidity` - which is not `newPool / pool`, but that times
`worstCase / ln2`. `b` and the phantom shares inflate by the extra factor
while the pool grows only by the contribution.

Worked, on the market the docs themselves name (Telarchy revenue, range
0-1000, reading 0, auto-funded 2000):

| step | b | shares | pool | worst case |
|---|---|---|---|---|
| anchored open | 511.24 | [1989.67, 0] | 2000 | 2000, solvent |
| inject 1e-9 (the legal minimum) | 2885.39 | [11229.42, 0] | 2000.000000001 | far past the pool |
| a trader then buys 5000 of `higher` | | 15738.79 held | 7000 | payout 15738.79 |

**8,738.79 credits created from nothing**, and the price never moved, so
nothing on screen says anything happened. `predictions.ts:117` detects
`totalPayout > pool`, logs "LMSR invariant violated", and pays anyway;
`poolLeftover` is floored at 0 so LPs cannot absorb it.

`every-open-anchors.test.ts:189` injects into an anchored book and asserts
only that the price is unchanged. The price is unchanged. The solvency is
not.

### 5. A market keeps taking buys after the number that settles it is public

`functions/src/services/trading.ts:88`

`executeTradeInTx` gates buys on `market.active` and nothing else. The
settling value is the last reading at or before the **period end**
(`predictions.ts:52`), but the market only becomes due at period end plus
`settlementLagMinutes` (`predictions.ts:187`), and nothing sets
`active = false` in between - `refreshRelativeDateMarkets` declares
`toDeactivate` and never pushes to it (`markets.ts:488,569`).

With the 3-day lag from the project's own fixture, September's settling
reading is logged and readable through `/api/metrics` on 1 October and the
market keeps quoting and filling until 4 October. Risk-free. Even at zero
lag the exposure is a full 10-minute resolver tick.

### 6. The key-minting gate, on its own (see 0 for the full takeover)

`functions/src/middleware/roles.ts:88`, fronting `functions/src/routes/agents.ts:1868`

`requireSelfOrAdmin` admits any caller holding `manage` whose target is a
member of their workspace. Self-join is the product model, so any
participant who joins a floor becomes "manageable" by that floor's owner -
and anyone can create a floor.

`POST /api/agents/<victim>/keys {"scopes":["*"]}` returns the victim's raw
secret. Keys are not `workspaceLocked` by default, so it authenticates in
**every workspace the victim belongs to**, including their own confidential
floor. The same gate fronts `/:id/wallet` (1725), `/:id/withdraw` (1752)
and `/:id/spend` (1542), so the same admin can repoint a co-member's payout
wallet or burn their balance.

### 7. A new floor is `unlisted`, and `unlisted` answers anonymous reads by name

`functions/src/routes/workspaces.ts:106`, `functions/src/lib/public-read.ts:40`

The UI sends `{name}` only, so a new floor is stamped `unlisted`.
`resolvePublicReadWorkspace` refuses only `private`; an unlisted workspace
whose Public group holds `read` (which `provisionWorkspace` seeds) resolves
for an anonymous caller, addressed by id **or slug**, case-insensitively,
globally. The slug is derived from the company name.

```
curl -H 'X-Workspace-Id: acme' https://telarchy.com/api/metrics
```

returns every metric name, description, formula and value, plus up to 500
points of history per metric. The only secret is a guess at the company's
own name. This is the direct answer to the open P1 in `TODOS.md`
("can a founder safely paste confidential KPIs into this hosted system"):
not through the UI's default path. Note the backend default is the safe one
(`services/workspace-create.ts:47` starts at `private`); the HTTP route
overrides it before calling in.

`functions/src/routes/admin.ts:373,484`

`POST /api/admin/agent-traces` and `POST /api/admin/agent-heartbeat` check

### 10. Rolling monthly horizons skip a month at month end

`functions/src/lib/date-utils.ts:71`

`d.setMonth(d.getMonth() + amount)` overflows. Run against the real module:

```
base 2026-08-30:  +1m -> 2026-09    +2m -> 2026-10
base 2026-08-31:  +1m -> 2026-10    +2m -> 2026-10     <- September lost, +1m and +2m collide
base 2026-01-31:  +1m -> 2026-03    +2m -> 2026-03
base 2026-03-31:  +1m -> 2026-05    +2m -> 2026-05
base 2026-05-31:  +1m -> 2026-07    +2m -> 2026-07
```

On the 31st, September is no longer a desired date, and `refreshMarkets`
**voids** an untraded market at a no-longer-desired date rather than
deactivating it (`markets.ts:544`), so September's market is destroyed and
never re-opened. A two-horizon metric silently loses one of its markets on
the same day. `src/lib/horizon-entries.ts:74` mirrors the bug, so the client
agrees with the wrong answer and the owner is never shown a discrepancy.

### 11. An unbounded relative horizon permanently 500s a workspace

`functions/src/routes/metrics.ts:787,833`

`RELATIVE_HORIZON_RE = /^\+(\d+)(h|d|w|m|y)$/` has no magnitude bound, so

### 13. The floor freezes your trade's price and then values your position on it

`src/pages/TradePage.tsx:193,800,855-865,1914`

`setLivePrice` is written in exactly one place - after your own trade lands
(line 800) - and is never cleared: not on poll, not on close, not on branch
switch. It is scoped to `activeMarketId`, so leaving the market clears it,
but staying does not.

While you stay, `livePrice` overrides `active.consensus` (line 865) even
though the 15-second poll keeps refreshing `active`. So the headline number
above the chart, both side ceilings (`:862-863`) and `PositionSummary`'s
"Worth now" and "Profit" (`:1914`) all sit at the price *your own trade*
landed at, while the chart line, the pool and the volume beside them move
with the market.

Alice's trade lands at $74,000. An hour later the market is at $120,000. The
chart shows $120,000; the big number still says $74,000, and her position is
valued at $74,000. She sells on a number that is an hour stale and hers
alone. The comment at `:191` shows the intent was one round-trip of optimism
before the reload lands; it was never given an expiry.

Worse, the same screen disagrees with itself: `TradeTicket` gets
`probability={active.probability}` (fresh, `:1875`) while `PositionSummary`
directly under it gets `livePriceProb ?? active.probability` (frozen,
`:1914`), so the ticket and the card print two different values for one
position. Inside the ticket, `PayoffLine` draws the "now" mark from the
frozen consensus and the breakeven from the fresh probability.

`AGENTS.md` names this class exactly: "Two surfaces that show the same fact
must derive it from the same place."

## P1

1. **`validateFormula` is dead code.** `functions/src/lib/metrics-engine.ts:76`
   is never called outside tests. `POST /api/metrics {formula: "revenue - costs"}`
   returns 201; bare identifiers are outside the grammar, so the parse throws,
   `evaluateFormula` catches and returns **0**, and the metric reads 0 forever
   with only a server log. `{Costs}` naming a metric called `Costs (USD)` does
   the same silently. `docs/formulas.md` says "the formula editor shows the
   error"; nothing does, on either side.

2. **`POST /api/metrics` never checks for cycles**, and
   `detectCircularDependency(null, formula, ...)` ignores its `formula`
   argument entirely (`metrics-engine.ts:163` matches on `m.id === null`).
   The graph does not hang, it goes inconsistent: A=`{B}+10`, B=`{A}*2`
   yields B=0, A=10. **`metrics-engine.test.ts:163` is the test for this and
   passes for the wrong reason** - its fixture is already cyclic, so it
   returns true no matter what formula is passed, including `'0'`.

3. **A market that settles negative can never resolve.**
   `services/predictions.ts:81`: `if (rawValue === null || rawValue < 0)` skips
   forever. `rangeMin` is caller-supplied and only validated as `rMax > rMin`
   (`routes/predictions.ts:946`), formulas support subtraction, and
   `metric-unit.ts:130` says outright that "a week's net can go negative".
   The market stays open past its date with every position's credits locked,
   logging an error on every cron run, with no cleanup job. `resolutionPayouts`
   already clamps, so the skip protects nothing.

4. **`sharesForBudget` silently under-fills a cheap side.** `lib/amm.ts:60`
   caps the binary search at `hi = budget * 20`, which binds whenever the
   average fill price is under 0.05. On a book anchored at `p = 0.02` with
   `b = 511`: a budget of 10 returns 200 shares for 4.87 charged, against
   351 shares the budget actually buys - a 43% under-fill. At Season 0 scale
   (b~2000) a budget of 50 can spend 3.21. `docs/guides/markets.md` promises
   "spends the whole budget, wherever that leaves the price". Every
   `sharesForBudget` case in `amm.test.ts` starts from `[0,0]` where the
   price is 0.5 and the bound never binds; `amm.test.ts:119` ("cost does not
   exceed budget") passes vacuously in exactly the failing case. The client
   mirror copies the same bound, so the ticket agrees and nobody sees it.

5. **Read-then-write on balances, three sites.**
   `POST /api/agents/:id/spend` (`agents.ts:1564-1576`) reads, checks, then
   calls `applyCredits(db, ...)` with no transaction and no conditional debit,
   so concurrent calls drive a balance negative. `/markets/liquidity/bulk`
   (`predictions.ts:1134-1156`) does the same. `approveProposal`
   (`proposals.ts:490,565`) checks `status !== 'pending'` on an unlocked read
   and its final update carries no `status = 'pending'` predicate, so a
   double-clicked Approve pays `proposalReward` twice - and approving is the
   payment.

6. **`POST /api/onboard/claim` is not idempotent.** `onboard.ts:231-239`
   checks outside the transaction and the update carries no
   `claimTokenHash`/`authUserId` predicate, so two in-flight claims of one
   token apply the 9,900-credit top-up twice. `onboard.test.ts:141` covers
   only the sequential retry.

7. **`/markets/liquidity/bulk` writes absolute state from a stale read.**
   `predictions.ts:1123` reads without `FOR UPDATE` outside the transaction
   and `:1167` writes absolute `shares`/`pool`. A trade landing in between is
   erased from the book while its position and trade rows survive, and is
   minted at settlement. `applyAgentLiquidityInjectionTx` takes the row lock
   correctly; this inlined copy does not.

8. **USDC deposits are not bound to the depositor.** `agents.ts:1697`
   destructures `from` out of `verifyUsdcDeposit` and never compares it to
   `agent.walletAddress`. Anyone can claim another person's on-chain deposit
   by posting their tx hash first, and `deposits.txHash` being the primary key
   makes it permanent. Also `agents.ts:1799`: a withdrawal whose RPC call
   times out **after** broadcast re-credits the full amount, paying twice.
   Both are behind `USDC_SETTLEMENT_ENABLED`, off on telarchy.com.

9. **The season scores workspaces published after the fact.**
   `routes/seasons.ts:669` and `routes/leaderboard.ts:502` pass every
   currently-public workspace and the window filter keys only on
   `markets.resolvedAt`. An entrant can trade a private floor all season and
   publish it minutes before settlement, contributing the whole month at once.
   `docs/seasons.md:133` documents the live set deliberately (owner decision
   2026-08-21) but the clause that would close this - *"A floor published
   mid-season counts from the moment it is public"* - is not implemented.
   `lib/board.ts:44-48` still carries the superseded D2 rationale and now
   contradicts both the doc and the code.

10. **Marked standings promise money the season cannot pay.** `board.ts:380`
    classifies an open market by `resolutionInstant(targetDate)` instead of
    `settlesOn(market)`, and never selects `markets.settlesAt`. A market
    resolving after `endsAt` because of its lag is marked into "Total if
    prices hold" and then dropped by the settled window's
    `lte(markets.resolvedAt, windowEnd)`. The column's own tooltip says
    markets resolving after the season ends are not counted.

11. **The season trade cutoff is measured against the wrong instant.**
    `board.ts:303` cuts 6 hours before `markets.resolvedAt`, but the outcome
    is fixed at the period end. Any metric with a lag over 6 hours leaves a

    trade still scores in full. `docs/legal/season-0-rules.md` promises the

12. **Nothing enforces one running season.** `services/seasons.ts:118` starts
    every due draft, and both `routes/seasons.ts:90` and
    `routes/leaderboard.ts:320` pick "the" running season with an unordered
    `limit(1)` / `find`, so two surfaces can price different seasons. The
    comment at `routes/seasons.ts:85` asserts the property the code does not
    enforce.

13. **`DELETE /api/agents/:id` 500s for any funded participant, and its blast
    radius is platform-wide.** `credit_transfers.from_agent_id`/`to_agent_id`
    reference `agents(id)` with no `ON DELETE` (`schema.ts:399-405`) and the
    handler never deletes those rows, so the transaction dies on `23503`.
    When it does succeed, `agents.ts:2096` deletes `trades` and `positions`
    with `eq(agentId, id)` and **no workspace filter**, unwinding LMSR state
    only in the caller's workspace - leaving another tenant's book carrying
    shares with no trades behind them.

14. **`removeProposal` accepts an approved contract.** `proposals.ts:730`
    short-circuits only on `status === 'removed'`, so deleting an approved
    $400 contract voids its live branch (refunding winning holders at cost)
    and erases the debt from `GET /api/admin/participants` and the data room.
    `proposal-removal.test.ts:79` deliberately seeds `declined` and never
    `approved`.

15. **The stale-reading nudge goes silent exactly when it is needed.**
    `reading-freshness.ts:36` measures against `periodEndInstant` and takes
    only `targetDate`, so it structurally cannot see the lag: it fires during
    the days the number legitimately cannot exist yet, and is silent through
    the lag window when the owner actually needs to file.
    `reading-freshness.test.ts:63` pins the pre-lag assumption.

16. **Prompt injection reaches privileged tool calls.**
    `services/otto-tools.ts:158` binds `call_api` to the caller's own cookie
    or agent key with no method or path allowlist beyond `/api/*`, while
    participant-written contract titles, descriptions and comments are
    concatenated into the **system turn** (`ask.ts:293`) with no fence - the
    fence exists only for web-search results. A contract description is
    enough to ask the owner's own assistant to approve it, and approving is
    the payment. `web-search.ts:81`'s `fence()` also does not strip its own
    terminator from the content, so a page can close the fence and speak
    unfenced. The file states the risk itself: the rule "is in the system
    prompt, not here".

17. **Bell "mark all read" resurrects the nudge.**
    `notifications.ts:1149` deletes every per-item read row while setting the
    watermark to now; the stale-reading item's `at` is in the future, so it
    is unread again on the next poll. The one action meant to clear the badge

19. **One failed poll replaces the live floor with a permanent error screen.**
    `TradePage.tsx:249` is the only writer of the page-level `error`, and
    there is no `setError(null)` anywhere in the component. A laptop waking
    before the network does fires a poll that rejects; every later poll
    succeeds and nothing ever clears the error, so the floor is gone until a
    hard reload.

20. **The open trade ticket is never reset when the market under it changes.**
    `setBetModal(null)` appears once in `TradePage.tsx` (`:1901`, the
    ticket's own X). Selecting another contract, metric or date re-points
    `active` while the ticket keeps its direction and amount, so a bet
    composed against one market is confirmed against another. The chart
    right above it does remount on a market change (`key={active.marketId}`);
    the ticket does not.

21. **The confirm button re-enables during its own success flash.**
    `TradeTicket.tsx:792` and `JobsBoard.tsx:397` both clear `busy` before
    the 1600ms / 900ms "✓ Placed" window ends, with the fields still filled,
    so clicking the checkmark to dismiss it places a second identical trade

22. **The report dialog rounds the prefill and files the rounded number.**
    `OwnerDialogs.tsx:587` seeds the field with `Math.round(lastValue)`. A

23. **"Approve, pay $N" reads the price out of the title prose.**

24. **Positions and limit orders are fetched with no request token.**

26. **A failed read is rendered as an empty truth, in four places.**

    `AnnouncementsPage.tsx:200` prints "Nothing announced yet." on a

## P2 (selected)

- **`resolutionPayouts` can pay more than 1 per matched pair.**
  `amm.ts:121` rounds both factors to 4dp independently. On a range wider
  than 10,000 units the two can sum to 1.0001 - on `[0, 20000]`, **7,362 of
  20,001 integer outcomes**, and the error is *always* toward the trader,
  never the pool. `predictions.ts:117` logs the overshoot and pays it.
- **Proportional season payout can over-commit the pool.** `seasons.ts:324`
  rounds each share up independently: 6 equal entrants on $100 assign
  $100.02 and report a **negative** rollover. `seasons.test.ts:249` is named
  *"cent rounding never overpays the pool; dust rolls"* and picks the one
  entrant count (3) that rounds down, so it cannot fail on the rule it names.
- **A `filled` limit order keeps its residual reservation forever**
  (`trading.ts:528`): `closeLimitOrderInTx` only ever selects `status = 'open'`,
  so up to 0.01 credits per order is debited and never returned.
- **Void rounds the LP pool up to whole cents** (`markets.ts:171`), so a
  sub-cent pool refunds more than was staked; `PATCH /api/proposals/:id` on
  an untraded pair loops the void/respawn and mints it.
- **`GET /api/predictions/markets` reports the wrong settlement instant**
  (`services/predictions.ts:369` uses `resolutionInstant`, every other reader
  uses `settlesOn`), so the list and the detail endpoint disagree by the lag.
  `docs/guides/markets.md` tells API traders to time on this field.
- **`market_resolved` activity is windowed in JS after the SQL `LIMIT`**
  (`services/activity.ts:138,329`), so a historical window silently shows
  zero resolutions. Every other source in the same function filters in SQL.
- **Every bell poll loads every permission group on the platform**
  (`notifications.ts:635`, no `where`), on a 15-second client poll.
- **Visit retention deletes unbounded with `RETURNING`**
  (`maintenance.ts:44`), two lines above the comment explaining why traces
  are chunked.
- **`X-API-Key: anything` disables the global and feedback rate limiters**
  (`app.ts:237`); `hasIdentity` is presence-only and the request is still
  served anonymously.
- **The shipped self-host CORS default reflects every origin with
  credentials** (`.env.example:45` + `origins.ts:22`). telarchy.com is
  unaffected.
- **Metric names are not unique per workspace** and formulas bind by name
  (`metrics-engine.ts:244`), so a duplicate name silently repoints every
  formula referencing it.
- **Workspace `name` has no length cap** on create or settings, and the slug
  is derived from it.
- **Slug resolution in the setup checklist is global** (`setup.ts:282`) where
  slugs are unique per owner, so one owner can be 403'd off their own floor.
- **Self-join is a read-modify-write of a JSON array**
  (`marketplace.ts:1818`, `workspaces.ts:827,898`), so a concurrent joiner
  is dropped while the API answers 201.
- **Manifold's two outbound fetches have no timeout and no size limit**
  (`manifold.ts:71,127`), unlike every other external call in the codebase.
- **`?ref=` is interpolated into the GitHub API URL unencoded**
  (`sources.ts:573,639`) - parameter injection, not SSRF.
- **`ref` docs that name files that do not exist**: `docs/vision.md:692` and
  `skills/telarchy-agent/SKILL.md:220` both instruct readers to see
  `scripts/hook-watcher.cjs`, which is not in the tree; `AGENTS.md:265`
  already calls it deprecated.
- **`seasons-autostart` is claimed by `AGENTS.md:296` and absent from the
  canonical cron table** in `docs/infra/deploy.md`. Worth checking against
  `gcloud scheduler jobs list` either way, given that doc already records
  months of silently dead cron jobs.
- **`DELETE /api/auth/me`'s JSDoc contradicts its own code**: the block
  comment says it works for both auth paths "so an API-key participant can
  also exercise their right to be forgotten"; the handler and `/api/help`

## Two things about the tests

The suite is large (188 backend files) and mostly good. Two patterns
recurred and are worth naming, because both produce green tests that guard
nothing:

**A test named after a rule it cannot exercise.** Three cases:
`seasons.test.ts:249` ("cent rounding never overpays the pool") picks the
entrant count that rounds down; `void-refund.test.ts:222` ("voiding twice
does not pay twice") is sequential, testing a guard that already exists;
`amm.test.ts:119` ("cost does not exceed budget") only ever starts from a
0.5 price where the failing bound never binds.

**A test that passes for the wrong reason.** `metrics-engine.test.ts:163`
reads as coverage for "the new formula is checked for cycles" and returns
true even when passed the formula `'0'`, because its fixture is already
cyclic. `custom-horizons.test.ts:72` asserts
`resolutionInstant(d) === periodEndInstant(d)` in a loop, which is the
implementation restated and cannot fail. `release-gate.test.ts:114` is a bare
`.rejects.toThrow()` with no matcher, so a `TypeError` from a refactor
satisfies it.

**A test that mocks the boundary it claims to integrate.**
`public-read-no-key.test.ts:57` says in its header that "the line these tests
hold is the whole design" and then builds three synthetic routes
(`/api/read-thing`, `/api/trade-thing`, `/api/member-thing`) rather than
mounting a real router, so dropping `requireIdentity` from a real endpoint
would not move it. `route-auth-matrix.test.ts:72` uses the workspace *owner*
as its "agent key" column, and the owner already holds every capability via
the `createdBy` shortcut, so removing `requireCapability('manage')` from a
workspace route cannot change its status. The same file at `:96` writes the
fixture itself when the file is missing and then compares against what it
just wrote.

**The gap that matters most.** The two files that decide who may act on
another participant's account - `middleware/roles.ts` and `routes/groups.ts` -
have no tests at all, and every suite that mounts a `requireSelfOrAdmin`
route stubs it to a pass-through. That is why P0-0 exists.

Nothing in the suite runs two money operations concurrently (`Promise.all([`
appears in exactly one test file), which is why every concurrency P0 above is
invisible to it.

Hygiene that came back clean: no `.only`, `.skip`, `.todo`, `xit` or
`xdescribe` anywhere; no snapshot files; the season settlement, void-refund,
limit-order, position-netting and earn-claim suites are genuinely thorough,
including arithmetic that re-derives correctly and at least one real race
test (`earn-claims.test.ts:71`).

## What was checked and found clean

Recording this because the sweep was the point, and because it says where
not to spend the next review.

- **Tenancy.** Every `.from/.update/.delete` on the 22 workspace-scoped
  tables across all 27 routers and 27 services was inspected. All are
  filtered on `workspaceId` at the route entry point. The single unfiltered
  read (`trading.ts:453`) is not reachable with a caller-supplied id.
- **`services/credits.ts` is a good design.** `applyCreditsIfSufficient`
  uses the conditional `UPDATE ... WHERE balance >= n` as its own check, so
  there is no overdraft race on any transfer or stake. `credits.ts:129` is
  genuinely the only writer of `agents.balance`, and a source-grep test
  keeps it that way. Integer nanocredits and `bigint` columns throughout; no
  float on balances anywhere.
- **`executeTradeInTx` takes both row locks, consistently ordered**, at all
  20 lock sites. Trade-vs-trade races are sound; only resolve, void and
  bulk-liquidity skip the lock.
- **The LMSR core is correct.** `lmsrCost`'s max-shift is the stable form,
  `pHigher` inverts it exactly, `betTowardsValue`'s signs are right,
  `anchoredMarketState`'s worst-case bound is exactly right for a fresh
  anchor (deficit 0.00), buy/sell round-trips are inverses to rounding, and
  redemption is genuinely price- and pool-neutral.
- **The formula tokenizer and parser are solid.** Precedence and
  associativity check out (`2^3^2` = 512, `-2^2` = -4), and `1e-3`, `.5`,
  `1.2.3`, `1_000`, `5%3`, `{}`, lone operators and empty input are all
  rejected with a column number. No `eval`.
- **The Stripe webhook is idempotent three ways** and verifies the raw-body
  HMAC with a 300s replay window before parsing.
- **No SQL injection.** Every `sql` fragment interpolates Drizzle column
  refs or bound parameters, never request strings.
- **The master key** is constant-time, single-reader, and now has a rotation
  grace window (`API_KEY_PREVIOUS`) - the prior finding about a hard cutover
  is fixed.
- **The beta `originalUrl` trap is fixed**: `route-policy.ts:83` keys on
  `baseUrl + path`, with the 2026-08-25 regression written up in place.
- **CI no longer runs fork PRs on the laptop** - `test.yml` is on
  `ubuntu-latest` with a gitleaks scan. The prior self-hosted-runner finding
  is stale.
- **`/api/help` is in sync with the registered routes** (193 entries; the
  only diffs are routes mounted outside the per-file routers).
