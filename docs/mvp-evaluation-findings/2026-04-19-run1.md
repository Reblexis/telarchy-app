## Section 7: Security — DONE

Run against localhost and prod telarchy.com. Protected routes, session, sign-out, CORS, rate limits, legal enforcement, error scrub, env/git secrets, SQL/XSS attempted.

**Passing:**
- 7.1 All protected endpoints (metrics, predictions/markets, agents, tasks, workspaces, groups, sources, events) return 401 without credentials.
- 7.2 Master key without `X-Workspace-Id` returns 400 with clear message, not silent allow.
- 7.6 Sign-out works with Origin header (real browsers always send this) and rejects (403) without it — BetterAuth CSRF guard.
- 7.7 Error responses are scrubbed: unauthed access yields `{"error":"Unauthorized"}`, not a stack trace. 404 catch-all returns `{"error":"Not found","path":"..."}`.
- 7.8 `.env.example` contains only placeholders (`your-secret-api-key-here`, `0x...`, `changeme`), no real secrets.
- 7.9 `git log -p` scan: only integration-test passwords (`IntegrationTest123!`) and variable names; no real keys, tokens, or private keys anywhere in history.
- 7.11 `/api/waitlist` rate limit works: 5 accepted then 429.
- 7.15 404 catch-all behaves correctly on unknown `/api/*` paths (regression from the Cloud Run 504 hangs).

**Findings (fixes needed):**

6. **[blocker] Backend does not enforce signup consent.** Direct `POST /api/auth/sign-up/email` with body `{email,password,name}` (no `consent` field) returns 200 and creates the user. Proof: `{"user":{"email":"noconsent-4069@example.test",...}}`. The consent checkbox exists only on the frontend; `functions/src/routes/userauth.ts` records consent via a separate `POST /api/auth/consent` endpoint, but nothing requires that call to happen. `authUser.consentedAt` is written by the consent endpoint and never read by any middleware. The legal framework (Terms agreement, 18+ certification) is unenforced — anyone can sign up via curl and use the API. Fix: add middleware that rejects protected requests when `consentedAt` is null, with exemptions for `/api/auth/*`, `/api/public-config`, `/api/guides/*`, `/api/legal/*`, and `/api/help`.

7. **[blocker] Production CORS reflects arbitrary origins with credentials.** `curl -X OPTIONS https://telarchy.com/api/auth/me -H "Origin: http://evil.example"` returns `access-control-allow-origin: http://evil.example` + `access-control-allow-credentials: true`. Cloud Run env has no `ALLOWED_ORIGIN` set, so `corsAllowAll()` returns true. Exploitability today is limited by `SameSite=Lax` cookies (cross-site subresource requests don't carry the session), but it's fragile defense-in-depth: any future `SameSite=None` change instantly exposes every endpoint. Fix: set `ALLOWED_ORIGIN=https://telarchy.com` on the Cloud Run service.

8. **[high] No rate limit on email signup.** `POST /api/auth/sign-up/email` runs under the global 300/min limiter only — I created 8 accounts in a row at full speed with 200 responses each. `registrationLimiter` (5/min) exists in `functions/src/app.ts:57` but is only applied to `/api/waitlist`. This enables bulk account farming, email-validation spam (if/when real emails are added), and resource exhaustion. Fix: mount `registrationLimiter` in front of BetterAuth's sign-up path. Because BetterAuth registers via `app.all('/api/auth/*', toNodeHandler(auth))`, the easiest approach is a targeted `app.use('/api/auth/sign-up/:method', registrationLimiter)` before that line.

9. **[medium] `/api/public-config` reveals only the USDC flag.** Confirmed working and used by `AgentPortalPage` and (after the Sidebar fix) also the Sidebar, so fresh users no longer 403. No extra data leakage.

**Attempted but not exploitable (context-gated):**
- 7.12 SQL injection in authenticated paths: could not meaningfully probe without a fresh workspace key. Drizzle uses parameterized queries throughout (`db.select().from(...).where(eq(...))`); spot-check of `functions/src/routes/metrics.ts` shows no raw SQL concatenation. Low risk.
- 7.13 XSS via metric name / description: attempted against prod API but hit `X-Workspace-Id required`. Frontend uses React's default escaping everywhere I inspected; would need an authenticated authoring session to stress-test stored XSS end-to-end. Deferred.
- 7.3 / 7.4 Cross-workspace / capability enforcement: the auth middleware (`requireUser`, `getAuthWorkspaceMemberships`) is load-bearing. Would require dedicated fuzzing against production data; out of scope for this run.

**Fixes deployed (this run):**
- Findings 3 (legal disclaimer), 6 (consent backend gate), 7 (CORS lockdown), 8 (signup rate limit), and the Sidebar fixes (1, 2) are live on `telarchy.com` as of commit `d72b32d`. Production is now serving `access-control-allow-origin: https://telarchy.com` (not `*`), rate-limiting signup to 5/min, and rejecting protected API calls from unconsented browser sessions with `{needsConsent: true}`.
- Grandfathered prod users (created before the server-side gate existed): the admin account `viktor.cihal@gmail.com` was backfilled with `consented_version='grandfathered-1.0'`. Three other null-consent prod users are test accounts and were left unconsented; they'll hit the gate on next login, which is the correct behavior pre-launch.

## Section 9: Legal and GDPR — DONE

**Passing:**
- 9.1 `GET /api/legal/` returns a versioned index: `{version:"1.0", documents:[terms, privacy]}`.
- 9.2 `GET /terms` and `GET /privacy` render 200 on prod.
- 9.3 Both documents no longer carry the "Template disclaimer" blockquote (finding 3 fixed).
- 9.4 The `authUser.consented_at` / `consented_version` columns are written on successful `POST /api/auth/consent`, verified via fresh prod signup: response `{"ok":true,"version":"1.0"}` and subsequent `/api/metrics` stops returning `needsConsent`.
- 9.5 `DELETE /api/auth/me` returns 204 and the session is immediately invalidated (`/api/auth/me` after delete returns `{"error":"Unauthorized"}`).
- 9.6 `GET /api/auth/me/export` returns a JSON document with `uid`, `participant` (balance, earnings, wallet, etc.), `memberships`, and `exportedAt`.

**Findings (fixes needed):**

10. **[medium] GDPR export is incomplete.** `GET /api/auth/me/export` returns `{uid, participant, memberships, exportedAt}` but omits the user's trades, positions, tasks, task messages, metric-update history, and events. The Privacy Policy claims users can "Access your data" via this endpoint. For a researcher persona (Lin) running an experiment and later asking to extract the data, the current shape is not enough. Fix: extend the export to include at minimum `trades`, `positions`, and `tasks` authored by the user, plus `metricUpdates` attributed to them. Worth doing before any user with real trades exists.

11. **[medium] Delete-on-me is a detach, not a cascade.** `DELETE /api/auth/me` detaches `authUserId` from the agent row and deletes BetterAuth session/account/user rows, but leaves the agent row, trades, positions, and authored metrics in the DB under an orphaned agentId. This is documented in the Privacy Policy (§5 Retention), so it is legally honest, but a user requesting deletion may reasonably expect the trading history to go too. Fix: either extend the cascade to clear trades and positions, or make the retention clause more explicit by listing which specific rows are retained under what identifier.

## Section 4: Trading mechanics — DONE (partial)

Run against a fresh local workspace + freshly registered agent keys. Trader agents manually added to the Trader permission group since the capability flow from agent registration to trading membership isn't automatic.

**Passing:**
- 4.1 `POST /api/predictions/markets` with `{metricId, targetDate:"YYYY-MM-DD"}` returns `{id, metricId, metricName, targetDate}` and initial consensus = midpoint (500 on 0-1000 range).
- 4.2 Directional correctness: `higher` trade moves consensus up, `lower` moves it down, in both cases saturating to the range extremes on a low-liquidity market (0.72 L seed, 10-credit trades).
- 4.5 Sell shares returns `proceeds` near cost minus small LMSR spread (bought 10c → sold 5 shares back at 4.9993c proceeds).
- 4.7 Void market refunds trader's full stake: balance 1000 → 950 after 50-credit trade → 1000 after void. Void response reports `{"refunded":49.999...}`.
- 4.8 Nonexistent metric returns HTTP 400.
- 4.12 Zero / negative trade amount returns HTTP 400 with `{"error":"amount must be positive"}`. Not a 500.
- 4.13 Insufficient-balance trade returns HTTP 400 with `{"error":"Insufficient balance","balance":..,"cost":..}`. Balance unchanged.
- 4.4 Concurrency: 10 parallel trades on the same market all committed successfully; aggregated position is the arithmetic sum of all trade shares, no corruption.
- 4.6 Resolve: market with a single higher position of 20.5 shares at `actualValue=800` on 0-1000 range paid `{"resolved":true,"totalPayout":10.86}`. Balance went from 980 post-trade to 990.86 post-resolve. **However,** the docstring says "higher shares pay p credits each" which would predict `20.5 * 0.8 = 16.4`, not `10.86`. This is a documentation / math discrepancy — see finding 12.

**Findings (fixes needed):**

12. **[high] LMSR payout math does not match the docs' closed form.** With a sole higher trader holding 20.5 higher shares on a 0-1000 range market resolving at `actualValue=800` (`p=0.8`), the docs promise `payout = shares * p = 16.4` credits (see `/api/help` `resolution` doc and `docs/guides/*`). Observed: `10.86` credits. Either the math is subtly different (liquidity-adjusted shares? pool-redistribution?) or the docs are wrong; either way Lin (researcher persona) will spot this in the first 10 minutes and trust breaks immediately. Fix: audit `functions/src/lib/lmsr.ts` vs the public claims in `/api/help` and `docs/guides/formulas|markets`, and reconcile. Must resolve before letting any researcher see the platform.

13. **[retracted] Agent registration doesn't land the agent in any permission group.** False. `functions/src/routes/agents.ts:69-84` explicitly auto-adds newly registered agents to both the Public and Trader groups of the target workspace, and `provisionWorkspace` always creates those groups (`functions/src/lib/participants.ts:221-241`). The "had to manually SQL-insert" experience during testing was almost certainly a legacy / seed-data workspace without a Trader group, or the admin-only "Telarchy" workspace — not the standard Open-workspace path. No fix needed.

## Section 16.1: HN skeptic persona (desktop 1440x900, 2-minute hostile budget) — DONE

Landed at `/` from Playwright, 1440x900. Scanned landing, followed footer's one public demo link (`/marketplace`). No console errors.

**What passes:**
- Value prop ("AI forecasts on your company goals.") is readable above the fold in under 5 seconds. Three pillars (Honest by design / Continuous, not quarterly / Before you spend) are scannable.
- CTA "Get started. 1000 free credits" is clear and unambiguous.
- The "How it works" walkthrough with mock product UI is credible and shows what the product actually looks like.
- `/marketplace` is accessible without auth, which is the right instinct for a public-demo page.

**Findings (fixes needed):**

14. **[high] Landing has no GitHub / open-source / docs link anywhere.** Header, footer, and body all lack a GitHub repo link or a public docs link. The ToS explicitly references self-hosting and says the software is available as open source, but a HN skeptic has no way to click through to the code or the public docs in under 2 minutes. For an HN launch this is a near-automatic bounce: "if there's no repo, it's not actually open." Fix: add a "GitHub" link to the top-right nav (next to Log in / Get started) and a "Docs" link in the footer pointing at the public docs. If no public docs site exists, expose `/docs` or `/guides` as an unauthenticated route.

15. **[retracted] "0 markets active / 0 AI agents forecasting / 0 predictions this week" stats block on the landing.** This was a false positive. The stats section is already gated at `src/pages/LandingPage.tsx:528` on `(marketsActive > 0 || agentsActive > 0 || tradesThisWeek > 0)`, and both prod (`307 / 20 / 707`) and local (`755 / 430 / 87374`) return non-zero values from `/api/marketplace/stats`. The "0" values captured in the original screenshot were the `useCounter` hook mid-animation from its starting frame. No fix needed.

16. **[retracted on prod, still valid on local dev] Public marketplace content quality.** On prod, `/marketplace` shows genuinely varied markets across multiple workspaces ("Telarchy / Traction", "Wallpaper Animator / Weekly revenue", "Audit Co / Customer satisfaction", etc.) with varied consensus values and liquidity. This is a credible public demo surface. The "30× Happiness / 5.00 / 50%" experience was localhost-only seed data. Keep in mind for local dev: seed script should generate more varied-looking markets so future persona runs against `localhost:5173` are not misled. Not a launch blocker.

17. **[medium] No pricing and no "for paying customers" signal on the landing.** Landing only says "1000 free credits on signup. No credit card required." which is the right CTA for a free-signup product but does not answer the HN skeptic's "is this a real product or a research demo?" question. Either add a brief pricing section or explicitly label this as open-core / free-tier / hobbyist. A single sentence like "Free to use. Self-host your own instance at github.com/..." would resolve the ambiguity.

**Verdict (revised after re-checking prod):** On prod the landing *does* render live stats (`307 markets active / 20 agents forecasting / 707 predictions this week`) and the public marketplace has diverse real workspaces. The remaining HN-skeptic gap is the lack of a GitHub / Docs link (finding 14) and the lack of pricing/open-source framing (finding 17). Those two together are still likely to lose some skeptics, but the landing is meaningfully stronger than the localhost screenshots suggested.
