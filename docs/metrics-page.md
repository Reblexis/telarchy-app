# The metrics page

`/{owner}/{slug}/metrics` is the owner's page. It answers the whole of their
recurring job in one screen: what this workspace is measured on, which dates
each number gets priced for, and how deep each of those markets runs.

It is not a settings page and it is not a cockpit. Everything on it is one of
those three things; anything else belongs elsewhere.

## Who sees it

The `manage` capability. A signed-in visitor without it gets the floor. There
is no link to it from a public page; the owner reaches it from the floor's own
account menu and from `/manage`.

## What it shows

One section per metric, in the workspace's metric order. Each carries:

- **The name**, as the floor prints it.
- **The description**, the sentence the market settles on, shown under the
  name. It is the metric's public definition, so the page renders it rather
  than a source label of its own.
- **The range**, `0 - marketRangeMax`, right-aligned in mono. A market prices
  a number inside a range; the owner cannot read a pool without it.
- **The credits a new market on this metric opens with.** Typed in credits,
  not in a multiplier. Empty means "the workspace default", which is stated
  once at the top of the page and is `newMarketLiquidityCredits`.
- **A chip per horizon**, one for every market this metric has open. The chip
  carries the date the market settles on, in words plus the resolved date
  (`This week - to 30 Aug`), and the market's current pool. A chip is a
  market: it links to it.

A metric with no horizon opens no market, and the page says so in place of the
chips: *"No market. Add a date and this number gets a price."* That sentence
is the page's only accent-coloured text, because it is the only state on the
page that costs the owner something.

## What it changes

- **Add a date.** Appends to `timePreference.customHorizons`; the refresh
  opens the market. The picker offers this week, this month, this quarter and
  this year, plus a typed date in any format the API takes (`YYYY`,
  `YYYY-MM`, `YYYY-Www`, `YYYY-MM-DD`, `YYYY-MM-DDTHH`). Dates already open on
  that metric are not offered twice.
- **Remove a date.** Drops it from `customHorizons`; the reconcile deactivates
  that market. A market with trades on it is not removed silently: the page
  says how many trades stand on it and asks again.
- **Set the credits.** Writes `liquidityCredits` on the metric. It applies to
  markets opened from then on, never retroactively, and the page says so.
- **New metric.** Name, description, range, and at least one date. A metric
  created without a date would be a settings row, not a market, so the date is
  required here even though the API allows it to be omitted.

Curve metrics (`timePreference.enabled`) keep working: their dates are
generated by the decay curve rather than listed, so their chips are read-only
and the section carries one control, *"use exact dates"*, which copies the
curve's current dates into `customHorizons` and turns the curve off. The
reverse is an API call, not a button; nobody has asked for it from a page.

## API

- `GET /api/metrics/overview` (read) returns exactly what the page draws:
  `{ defaultCredits, metrics: [{ id, name, description, rangeMin, rangeMax,
  credits, curve, horizons: [{ marketId, targetDate, label, pool, trades }] }] }`.
  Composing this in the browser would take two calls and a join over markets
  the client has no other use for.
- `PUT /api/metrics/:id` takes `liquidityCredits` (a number, or `null` to fall
  back to the workspace default) alongside the fields it already takes.
  Horizon edits go through the `timePreference` it already accepts.

## Why credits and not weights

A weight is a multiplier on a number set on another screen. To know what a
market opens with, the owner has to hold two numbers and multiply. Credits are
what the pool is denominated in and what the chip shows, so the control and
its effect are in the same unit on the same screen.
