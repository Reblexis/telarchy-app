## Friction found
- [high] F1 — GDPR right-of-access endpoint returns an incomplete record. `GET /api/auth/me/export` does not include: (a) the user's own email address; (b) display name; (c) consent timestamp and version; (d) trades, positions, proposals, metric-updates authored by the user (Privacy Policy §1 explicitly lists these as collected); (e) OAuth provider profile data if the user signed in via Google/GitHub. Under GDPR Article 15, the controller must provide a copy of *all* personal data being processed, with limited carve-outs. The current export ships the internal `apiKeyHash` (which Noor does NOT need) while omitting the email address (which Noor specifically wants). This is a direct inconsistency with the Privacy Policy's representation of the endpoint. Severity: this is the single biggest privacy-posture weakness; a DPO writing a subject-access response today would need to query the DB manually. Extend the export to include authUser fields (email, emailVerified, consentedAt, consentedVersion, name), trades, positions, proposals owned by participant, metricUpdates by participant; drop the `apiKeyHash` field.
- [medium] F2 — No frontend handling of `needsConsent: true`. The server correctly returns 403 with `needsConsent: true` if an authenticated user has no consent record (e.g. OAuth-return race, cleared sessionStorage, or a future consent-version bump). No client code in `src/` reads the `needsConsent` flag (`grep needsConsent src/` returns zero matches). Result: a user in this state sees a generic "Forbidden" or blank state with no path to re-consent. Simple fix: in the global fetch wrapper (`src/lib/api.ts`), on 403 with `needsConsent`, redirect to `/consent` or show an interstitial modal. Today this is latent but easily triggered by clearing sessionStorage mid-signup.
- [medium] F3 — Privacy Policy §1 lists `request logs: IP address, user-agent, and basic request metadata` but there is no way for a user to access or delete these. The policy says they're retained "typically 30 days"; there's no mechanism to honor an Article 17 erasure request for request logs specifically. In practice request logs are legitimate-interest processing and rarely challenged, but the gap should be named: either expose a coarse-grained export ("count of requests in last N days") or clarify in §5 that request logs are NOT covered by the `DELETE /api/auth/me` endpoint.
- [low] F4 — OAuth consent gate stores `pendingConsent` in `sessionStorage` and records it after the OAuth return via an effect in `LandingPage.tsx`. If the OAuth callback lands anywhere that doesn't mount LandingPage (e.g. a future deep-link redirect), consent is silently never recorded, and the user then hits F2. Robustness could be improved by recording consent server-side at OAuth-callback time (signed-up-via-OAuth signals consent was captured client-side; record it then).
- [low] F5 — Legal contact is a personal gmail (`viktor.cihal@gmail.com`) in both ToS §12 and Privacy §11. Legible as early-stage. Flagged so the user can decide if it's intentional.

## What worked
- ToS and Privacy render cleanly with no unresolved placeholders. Every claim I could verify (Delaware law, 18+, no analytics, BetterAuth + GCP as processors, detach-based deletion) matched live behavior.
- Consent checkbox is unticked by default, submit disabled until checked. This is the shape Article 7 expects (clear, affirmative, specific).
- Server-side consent enforcement (`requireConsentIfUser`) is active on /api. Even if a client bypasses the checkbox, no API call works without a consent record. This is stronger than the client-side gate and what you want.
- Detach-based deletion is *honestly documented* as detach-not-hard-delete. Noor would tell a colleague "they're being more honest than most SaaS about what deletion means".

## Would they come back?
Yes, but only after F1 is fixed. If the export endpoint returns at least email + consent record + trades + positions, Noor is likely to sign up and stick around. Today, Noor would sign up, exercise the export endpoint, notice the gap, and either bounce or write a pointed email to the contact address.

## Recommended changes
- [high] Extend `GET /api/auth/me/export` to return: authUser record (id, email, name, emailVerified, consentedAt, consentedVersion), trades (by participantId), positions, proposals created, metricUpdates authored. Drop `apiKeyHash` from the export (it's a secret hash, not user-readable data). (This is partially the deferred finding 10 from `docs/mvp-evaluation/findings/2026-04-19-run1.md`; this persona re-confirms it.)
- [medium] Handle 403 `needsConsent:true` in the global API client. On first occurrence, redirect to a `/consent` interstitial that posts consent and then retries the original action. Prevents the stuck-at-403 failure mode.
- [medium] Record consent on the server side at OAuth callback as a fallback. Client already posts consent from LandingPage; the server can mark consent accepted on first post-OAuth API call from a user whose client has set a signed "consent-accepted-at-signup" marker. Belt-and-suspenders.
- [low] Update Privacy §5 Retention to explicitly name request logs as outside the `DELETE /api/auth/me` scope, or remove them from §1 if they're actually deleted on the rolling 30-day window without user action (probably the latter is already true and just needs to be said).
